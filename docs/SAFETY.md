# Safety: правила, без которых этот проект нельзя запускать на живой машине

Kext — это код в kernel space с доступом к MSR. Ошибка здесь стоит не «перезапустить демона»,
а «чёрный экран, потеря данных, поход за отвёрткой». Поэтому safety — не раздел в конце, а
часть архитектуры.

## 1. Модель угроз

| Что может сломаться | Причина | Последствие |
|---|---|---|
| Паника ядра | неверный MSR, гонка, bad pointer | reboot, потеря несохранённого |
| Зависание SMU | неверный SMU message ID / аргумент | чёрный экран, только power-cycle |
| Все ядра на 800 МГц | демон умер, watchdog не сработал | система «жива», но непригодна |
| Перегрев | guard отключён/обойдён | троттлинг, shutdown, деградация |
| Sleep не работает | неверный revert/reapply | ноутбук не просыпается |
| Потеря данных | паника во время записи | повреждение FS |

## 2. Watchdog

- Демон шлёт `heartbeat` каждые **50 мс**.
- Kext считает пропуски. **3 пропуска (150 мс) → auto.**
- Auto — это не «все на 800», а безопасный balanced:
  `max = highest_perf`, `min = lowest_perf`, `desired = nominal_perf`, `EPP = 128`.
  Система остаётся отзывчивой, просто без агрессивной экономии.
- Watchdog живёт в kext, не в демоне. Демон не может «продлить себе жизнь» иначе как
  heartbeat'ом.
- Watchdog не отключается флагом из userspace. Только выгрузкой kext / boot arg.

Почему 150 мс, а не 1 с: если демон умер, 1 с на 800 МГц — это заметный лаг. 150 мс — уже
неприятно, но переживаемо. Почему не 50 мс: демон может быть вытеснен планировщиком; ложные
срабатывания хуже.

## 3. Boot arg kill switch

- `ryzenplatform=0` или флаг `-ryzenpmoff` — kext проверяет boot arg в `start()` и не
  активируется (оба спеллинга реализованы в коде, `disabledByBootArg()`).
- Дублирующий путь: OpenCore entry с этим аргументом, всегда доступный.
- Если kext всё равно грузится (например, забыли аргумент), второй рубеж — `resetAuto` по
  таймауту и thermal guard.

## 4. Sleep / wake

- Перед сном: `resetAuto`, снять override, остановить watchdog-таймер.
- После пробуждения: заново прочитать caps, включить CPPC, запустить watchdog, дождаться
  первого heartbeat, только потом применять политику.
- Если демон не проснулся/не прислал heartbeat — остаёмся в auto. Не «догоняем» политику
  вслепую.
- Тест: 20 циклов sleep/wake, включая sleep под нагрузкой и sleep сразу после клика.

## 5. Дисциплина записи

- Перед каждой записью: clamp в `[lowest_perf, highest_perf]`.
- После каждой записи: read-back; не совпало — считать запись неудачной, отключить override.
- Никаких записей «на всякий случай» в чужие MSR.
- Запись `CPPC_REQ` — таргетным вызовом на один CPU, а не `mp_rendezvous` на все ядра (см. TZ §3.3).
- SMN index/data делить с другими kext'ами нельзя без защиты: свои обращения под локом, чужие
  ловить повторным чтением индекса; растущий `smn.retries` = остановиться и разбираться.
- Никаких записей в SMU mailbox в v0.1.
- Никаких voltage/CO.
- Если CPU не тот (не Family 19h / не Cezanne) — kext не активируется, логирует и выходит.
- Если CPPC не supported — kext не активируется. Никаких «попробуем всё равно».

## 6. Тепловой guard

- В kext, независимо от демона:
  - T > 90 °C → cap `nominal`;
  - T > 98 °C → все `lowest`, EPP 255;
  - T > 100 °C → `resetAuto` + лог.
- Демон может быть консервативнее, но не может поднять лимит выше kext'овского.
- Если температура недоступна (сенсор молчит) — считать, что guard активен, и не давать
  агрессивный буст. «Нет данных» ≠ «всё хорошо».

## 7. Логирование

- Ring buffer в kext: timestamp, core, old/new perf, EPP, причина, результат read-back.
- Выгрузка через user client; `IOLog` — только для старта/стопа/ошибок.
- Демон пишет CSV/JSON: время, состояние, urgency, решение, фактические частоты, температура,
  мощность, frame time.
- После паники: если есть возможность, сохранить ring buffer на диск при следующей загрузке
  (демон забирает его до применения политики).

## 8. Протокол тестирования

0. **Чтение** — `ryzenstat -w 5` в простое и под нагрузкой: `cppc.enabled`, C0%, Tctl,
   `smn.retries`. Пока там нет вменяемых данных, никаких записей.
1. **Симулятор** — политика без железа.
2. **Одно ядро** — задать low/high, проверить APERF/MPERF, вернуть auto.
3. **Все ядра, малые пределы** — не ниже 2 ГГц, не выше nominal, 10 минут.
4. **Watchdog** — `kill -9` демона под нагрузкой, замерить revert.
5. **Sleep/wake** — 20 циклов.
6. **Soak** — 8 часов со смешанной нагрузкой.
7. **Recovery drill** — имитация «плохого kext»: boot arg, запасной EFI, загрузка без kext.

## 9. Красные линии

- Не тестировать на единственной рабочей машине без бэкапа.
- Не запускать «на удалёнке» без физического доступа к питанию.
- Не отключать thermal throttling.
- Не писать в SMU mailbox без verified ID и recovery-плана.
- Не оставлять демона без watchdog.
- Не обещать «все ядра на 4.4».
